# 二次开发文档二

> 本次改动的目标只有一个：

- 让 TrendRadar 的本地数据目录支持统一配置，便于本地调试和服务器部署使用同一种目录挂载方式。

## 你实际要改哪个路径

只改这一个文件里的这一个配置：

- [docker/.env](/Users/changhuanli/explore/TrendRadar/docker/.env:15)

需要改的字段：

```env
SHARED_OUTPUT_DIR=../output
```

你以后在服务器上，改成你服务器的共享目录即可，例如：

```env
SHARED_OUTPUT_DIR=/data/trendradar/output
```

这就是你主要需要改的路径。

不要优先改：

```env
LOCAL_DATA_DIR=/app/output
```

这个值表示**容器内路径**，默认保持不动即可。  
除非你明确要改容器内目录结构，否则不要动它。

## 改动后的行为

改动后，目录关系变成这样：

- 宿主机目录：`SHARED_OUTPUT_DIR`
- TrendRadar 容器内目录：`LOCAL_DATA_DIR`，默认 `/app/output`

TrendRadar 会在容器内读写：

- `/app/output/news/YYYY-MM-DD.db`
- `/app/output/rss/YYYY-MM-DD.db`
- `/app/output/html/...`

但这些文件真实落在宿主机的：

- `SHARED_OUTPUT_DIR/news/YYYY-MM-DD.db`
- `SHARED_OUTPUT_DIR/rss/YYYY-MM-DD.db`
- `SHARED_OUTPUT_DIR/html/...`

也就是说：

- 你改 `SHARED_OUTPUT_DIR`
- TrendRadar 就会把数据写到新的共享目录
- 你未来的后台容器只要挂同一个宿主机目录即可读取

## 为什么这样改

之前的问题是：

- Docker Compose 挂载目录写死在 `../output`
- 项目内部也有多处把 `output` 写死
- 本地和服务器容易形成两套路径理解

这次改完后：

- Docker 挂载改为可配置
- 应用内部读写目录统一走配置
- MCP 查询侧也跟着同一个目录读取

这样可以保证：

- 本地和服务器部署方式一致
- 宿主机只需要维护一个共享目录
- 后台项目以后只需要挂载同一个目录，不需要进 TrendRadar 容器里找文件

## 本次涉及范围

本次只改了“数据目录配置”相关内容，主要包括：

- Docker 环境变量和 volume 挂载
- 主程序里的输出目录硬编码
- MCP 读取侧的数据目录硬编码
- doctor 体检输出目录

没有改：

- 抓取逻辑
- 分析逻辑
- 通知逻辑
- 数据库表结构
- 后台项目实现

## 现在怎么用

### 本地调试

你可以先把：

```env
SHARED_OUTPUT_DIR=../output
```

改成你真正想长期使用的本地共享目录，例如：

```env
SHARED_OUTPUT_DIR=/Users/changhuanli/data/trendradar/output
```

这样你本地就和服务器思路一致了。

### 服务器部署

服务器上只需要改：

```env
SHARED_OUTPUT_DIR=/data/trendradar/output
```

然后确保：

- 这个目录存在
- Docker 有权限挂载

TrendRadar 容器就会把数据写到这里。

## 你未来后台项目该怎么接

后台项目如果也是 Docker 容器，只要把同一个宿主机目录挂进去即可。

例如宿主机共享目录是：

```txt
/data/trendradar/output
```

后台容器里可以挂成：

```txt
/data-source
```

然后后台读：

```txt
/data-source/news/YYYY-MM-DD.db
```

后台要的是“当天累计去重后的全部新闻”，就查：

- `news_items`
- 需要平台名时连 `platforms`

## 验证情况

本次已经验证：

- 默认配置下仍然使用原来的 `output` 目录
- 设置 `LOCAL_DATA_DIR` 后，应用内部读取和输出目录会同步变化
- `trendradar --doctor` 可以识别当前数据目录
- 相关 Python 文件已通过语法校验

## 风险说明

当前方案的前提是：

- 两个项目部署在同一台服务器

只要这个前提不变，这个方案就是最简单、最稳的。

如果以后变成两台服务器，再考虑：

- 对象存储
- API

在当前阶段，不建议提前复杂化。
